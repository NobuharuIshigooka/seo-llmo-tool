# スコアリング仕様

**このファイルがスコアの唯一の定義。** 実装は `app/scoring.py` に集約し、他のファイルに配点や閾値をハードコードしない。

## 基本方針

**すべてルールベースで算出する。Claude API に点数を判断させない。**

理由：同じサイトを2回診断してスコアが変わると、営業ツールとして信用を失う。同一入力からは必ず同一スコアが出ることを保証する。

Claude API の役割は自然文の生成のみ（`docs/api-integrations.md` 参照）。

## カテゴリ配点

| カテゴリ | 配点 |
|---|---|
| テクニカルSEO | 30 |
| コンテンツSEO | 30 |
| LLMO対応度 | 35 |
| **合計** | **95 → 100点換算** |

各カテゴリは内部で100点満点に正規化してから重み付けし、3カテゴリ合計95点を100点に換算する（`compute_total_score`）。

被リンクを診断・スコアに一切使わない方針にユーザー判断で変更（`docs/progress.md` 参照）。

**2026-08-24：LLMO対応度の配点を25→35に変更し、「情報構造・発見巡回」系の新規7項目を追加した**
（ユーザー要望）。既存5項目（FAQ〜AI Overview引用）はそのまま維持し、新規7項目（当初素点合計40）を
別枠として追加。LLMO内部の素点合計は100→140になり、この140点をカテゴリ配点35点に正規化する。

**2026-08-24（同日追記）：重複していた構造化データ判定を統合した。** テクニカルSEOの「構造化データ」
（JSON-LD有無のみ）とLLMOの新規項目「構造化データ（LLM可読性）」（JSON-LDのパース成否）が、
いずれもLLMOの「FAQ / QA構造化データ」（FAQPage/QAPage/HowTo型の有無）と実測値が重複していた
（ユーザー指摘）ため、両方を廃止し配点をFAQ/QA構造化データに統合した。
テクニカルSEOで空いた20点は残り4項目に均等配分（各+5）、LLMOで空いた8点はFAQ/QA構造化データに
上乗せ（25→33）。詳細は本ファイル「①テクニカルSEO」「③ LLMO対応度」節を参照。

### 未計測カテゴリの扱い

PageSpeed Insights が失敗した場合など、計測できなかったカテゴリは**総合スコアから除外し、残りの重みで正規化する**。推定値で埋めない。

画面には該当カテゴリを「未計測」と明示する。

## ① テクニカルSEO（30点）

| 項目 | 配点 | 判定 |
|---|---|---|
| 表示速度（モバイル） | 45 | PSI performance score に比例 |
| 表示速度（PC） | 15 | 同上 |
| モバイル対応 | 20 | viewport メタタグの有無 |
| クロール可能性・HTTPS | 20 | noindexでない 10.67 / canonical 5.33 / HTTPS 4 |

**2026-08-24：「構造化データ」（JSON-LD有無のみの判定、旧20点）を廃止した。** LLMOの
「FAQ / QA構造化データ」（FAQPage/QAPage/HowTo型の有無）と判定内容が重複していたため
（ユーザー指摘）。空いた20点は残り4項目に均等配分した（各+5、旧クロール可能性15点の内訳
noindex8/canonical4/HTTPS3の比率は維持したまま20点にスケール）。

## ② コンテンツSEO（30点）

| 項目 | 配点 | 判定 |
|---|---|---|
| 本文の情報量 | 30 | **2,500文字で満点**（日本語のため文字数で評価。空白除去後） |
| キーワード網羅性 | 25 | 推定キーワードのページ内出現率に比例 |
| タイトル・見出し構造 | 25 | 下記の内訳 |
| E-E-A-T要素 | 20 | 検出数 / 4 で比例（4種以上で満点） |

**タイトル・見出し構造（25点）の内訳**

| 小項目 | 配点 |
|---|---|
| title が20〜40文字 | 8（範囲外だが存在すれば4） |
| H1 が1つだけ | 6（2つ以上は2、無しは0） |
| H2 の数 | 1個につき1.5、最大6 |
| meta description が60文字以上 | 5（存在するが60未満なら2） |

**E-E-A-T要素の検出対象**：運営者情報／著者・監修情報／連絡先／実績表記／資格・許認可

## ③ LLMO対応度（35点）

内部の素点合計は140点（既存5項目108点＋新規項目32点）。この140点を35点に正規化する。

### ③-a 既存5項目（素点108）

| 項目 | 配点 | 判定 |
|---|---|---|
| FAQ / QA構造化データ | 33 | FAQPage / QAPage / HowTo のいずれかがあれば満点 |
| Q&A形式の見出し | 20 | 疑問形・解説形の見出し1個につき4、最大20 |
| 冒頭の定義文 | 20 | 冒頭段落が40〜200文字なら満点、範囲外だが存在すれば10 |
| リスト・表による整理 | 15 | ul/ol/table 1個につき2.5、最大15 |
| AI Overview での引用 | 20 | 下記参照 |

**2026-08-24：FAQ / QA構造化データを25→33に変更した。** 後述の新規項目「構造化データ
（LLM可読性）」（旧8点、JSON-LDのパース成否を判定）が本項目と実測値の面で重複していたため
（ユーザー指摘）、廃止して配点をここに統合した。

**AI Overview での引用（20点）**

- AI Overview が表示されたキーワードのうち、自社が引用された割合に比例
- **AI Overview が1件も表示されなかった場合は減点対象とせず、中立評価（50%＝10点）とする**

**Q&A形式の見出しの判定**：見出しに `?` `？` または「とは」「なぜ」「どう」「方法」「できる」「違い」「いくら」「おすすめ」を含むもの

### ③-b 新規項目：情報構造・発見巡回（素点32、2026-08-24追加）

ユーザー提示の12項目のうち、既存カテゴリ（テクニカルSEO／コンテンツSEO）と実測値が重複する
5項目（H1構造・ページタイトル文字数・ページ説明文文字数・canonical有無・noindex有無）は
LLMO側には追加しない（重複配点を避けるため。それぞれ既存の「タイトル・見出し構造」
「クロール可能性・HTTPS」で採点済み）。

当初は「構造化データ（LLM可読性）」（JSON-LDのパース成否を判定、8点）も追加していたが、
③-aの「FAQ / QA構造化データ」と実測値が重複していたため同日中に廃止し、配点をFAQ/QA構造化データに
統合した（③-a参照）。そのため新規項目は最終的に6項目、素点合計32点になっている。

| 項目 | 配点 | 判定 |
|---|---|---|
| mainタグ | 5 | `<main>`要素が1個のみで満点。0個・2個以上は0点 |
| 見出し数 | 5 | h1〜h6の合計数。5個以上で満点、2〜4個で2点、0〜1個で0点 |
| 本文ブロック | 5 | `<article>`と`<section>`の合計数。3個以上で満点、1〜2個で2点、0個で0点 |
| robots.txt | 5 | 設置あり・かつ全面Disallowでなければ満点。未設置または全面Disallowは0点 |
| sitemap.xml | 5 | `/sitemap.xml` が取得できれば満点、できなければ0点 |
| llms.txt | 7 | `/llms.txt` が取得できれば満点、できなければ0点 |

**判定方法の実装**：`app/clients/crawler.py` の `fetch()` が診断対象URLの `/robots.txt`
`/sitemap.xml` `/llms.txt` を追加取得し、`CrawlResult` に格納する。robots.txtの取得は
既存のクロール可否判定（`RESPECT_ROBOTS`）と同じリクエストを流用し、二重取得はしない。

## 改善インパクトの算出

各項目について「失点 ÷ カテゴリ内の素点合計 × カテゴリ重み」を計算し、大きい順に上位3件を「最初に着手すべき項目」として提示する。

2026-08-24：旧実装は「失点 ÷ 100」で固定していた（各カテゴリの素点合計が100点である前提）。
LLMO対応度の新規7項目追加でLLMO内部の素点合計が140点になったため、カテゴリごとの実際の
素点合計で正規化する式に修正した（テクニカルSEO・コンテンツSEOは素点100のままのため計算結果に影響なし）。

## 閾値の運用（重要）

**本文2,500文字などの満点ラインは暫定値。運用開始後（工程6）に実際の診断結果を10〜20件確認して調整する。**

調整時は `app/scoring.py` の定数のみを変更すれば済む構造を維持すること。

### 改訂検討事項（未着手・ユーザー指示待ち）

- **2026-08-20：LLMO対応度におけるFAQ/QA構造化データの配点比重が過大ではないか（ユーザー指摘）**
  「FAQ / QA構造化データ」（25点）と「Q&A形式の見出し」（20点）を合わせると、LLMO対応度25点のうち
  45点分（正規化前の素点ベース）がFAQ関連の判定に依存している。一方、診断は`docs/requirements.md`の
  設計上トップページのみが対象であり、日本のコーポレートサイトはFAQをトップページに置かず、
  お問い合わせ・製品ページ等に分散配置するケースが多い。そのため業種によらず一律で
  この項目を落としやすく、「トップページのみ診断」という制約と「FAQを主要判定軸に置く」配点設計の
  間にミスマッチがある可能性がある。
  対応方針は未確定。工程6の実サイト診断10〜20件（本セクション冒頭の閾値調整タスク）で
  実際の該当率を確認してから、配点を下げる／Q&A見出しや冒頭定義文など他のトップページで
  実現しやすい項目に重みを移す等の要否を判断する。**変更はユーザーからの指示があってから着手する。**

- **2026-08-20：LLMO対応度の残り項目（FAQ以外）を「トップページ限定診断」の観点で評価**
  上記のFAQ指摘を受けて、LLMO対応度の他4項目についても同じ観点（業種を問わずトップページで
  実現しやすいか）で洗い出した。配点を動かす場合の参考として記録する。

  - **冒頭の定義文（20点）**：トップページ診断と最も相性が良い項目。「このサイトは何か」を
    冒頭40〜200文字で述べるのは業種を問わないトップページの基本的なライティング作法で、
    構造化データや専用セクションの新設が不要。**配点を維持、あるいは強化する候補。**
  - **Q&A形式の見出し（20点）**：`h1`/`h2`にキーワード（「とは」「なぜ」「方法」等）を含むかの
    簡易判定で、FAQPage等の専用構造を要求しない分トップページでも実現しやすい。ただしキーワード
    マッチのみのため、文脈と無関係にヒットする過剰検出の可能性は残る（E-E-A-T検出と同種の簡易判定、
    `docs/progress.md` 工程3の備考も参照）。実サイト検証で過剰検出がないか要確認。
  - **リスト・表による整理（15点）**：`ul`/`table`要素数の機械的カウント。ビジョン・沿革などを
    文章主体で語るデザイン重視のコーポレートサイトは箇条書きが少なくなりがちで、FAQと同系統の
    「機械的な構造カウントがトップページのデザイン傾向に左右される」弱点を持つ。ただし配点が
    15点とFAQより小さく、影響度は限定的。
  - **AI Overview での引用（20点）**：設計は妥当と判断。AI Overviewが表示されないキーワードは
    中立評価（50%＝10点）とする配慮が既にあり、「たまたま表示されなかったから0点」という
    不公平は回避されている。ただしこの項目のスコアは対策キーワードの抽出精度に強く依存する
    （キーワード抽出がズレればAI Overview引用判定もズれる）。これはLLMO配点固有の問題というより
    診断全体の品質に連動する間接的なリスク。

  **配点を調整する場合の一貫した方向性**：FAQ・リスト表（機械的な構造カウント系）の配点を下げ、
  冒頭定義文（トップページのライティングで完結する項目）に重みを寄せる、という調整が
  「トップページ限定診断」という制約との整合性が高い。ただし**これも実サイト検証データを見てから
  判断する。変更はユーザーからの指示があってから着手する。**

## 表示要件

- 各項目には**実測値を根拠として必ず併記**する（例：「本文 約1,240文字」「表示速度スコア 62／100」）
- 商談で外部ツール名（PageSpeed Insights等）を出さない。根拠文言は自社指標であるかのような表現にする（2026-08-21、ユーザー判断）
- 商談中に「その点数の根拠は？」と聞かれて答えられない項目を作らない
- 数値の羅列を避け、スコア・ゲージ・バッジ等の視覚要素を中心に提示する
- `rubric_version` を結果JSONに含め、配点変更の前後を区別できるようにする
